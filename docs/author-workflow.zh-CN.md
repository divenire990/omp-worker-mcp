## 1. 可复用架构：主控 Harness 与 Worker 模式

`omp-worker-mcp` 基于协议中立的本地 stdio MCP 设计。任何能够启动本地 stdio MCP 子进程的主控 Harness（如 **Codex**、**Claude Code**、**WorkBuddy**、**Cursor**、**Cline**、**VS Code**、**GitHub Copilot CLI** 等）均可在满足本地运行时前提下充当主管编排者，将具体自治任务单元下发给后台 OMP Worker 执行。

```text
┌────────────────────────────────────────────────────────────────────────┐
│                          主要主控 Harness                              │
│                  (Codex / Claude Code / WorkBuddy)                     │
│                                                                        │
│  1. 理解任务目标  ──▶  2. 拆分 / DAG 编排  ──▶  3. 设定验收标准         │
│         ▲                                                 │            │
│         │ (6. 通过 omp_continue 进行同会话纠错)           │            │
│         │                                                 ▼            │
│  5. 验收结果产物  ◀──  4. 委派执行并持续监督 ──────┘            │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ 本地 stdio MCP 协议
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│                            omp-worker-mcp                              │
│              (状态持久化、并发控制池、DAG 拓扑解析与安全校验)              │
└───────────────────┬────────────────────────────────┬───────────────────┘
                    │                                │
                    ▼                                ▼
       ┌─────────────────────────┐      ┌─────────────────────────┐
       │   OMP Worker (任务 A)   │      │   OMP Worker (任务 B)   │
       │   [write: src/feature/] │      │   [read_only: docs/]    │
       └─────────────────────────┘      └─────────────────────────┘
```

> **支持边界说明**：
> 文中列举具体 MCP 客户端仅用于说明兼容的本地 stdio 配置方式。不同客户端的配置格式与运行行为需用户在本地自行验证；提及具体产品**不代表**已获得官方认证、持续集成保证或上游产品的官方背书。

## 2. 主控 Harness 监督闭环流程

标准监督闭环包含以下 6 个核心阶段：

1. **理解与定界（Understand & Contextualize）**：解析用户目标，执行轻量有界的只读调研，确认工作区前置依赖。
2. **拆分与编排（Decompose & Schedule）**：评估任务复杂度，决定是直接处理、委派单一任务，还是构建拓扑 DAG 批处理任务组。
3. **设验收与边界（Define Acceptance Criteria & Boundaries）**：显式设定可验证的验收标准（`acceptance`），设置访问模式（`read_only` 或 `write`），并为写入任务分配互不重叠的 `ownership` 路径。
4. **委派与监督（Delegate & Supervise）**：调用 `omp_run_compact`、`omp_delegate` 或 `omp_run_batch_compact` 启动后台执行，主会话保持持续响应。
5. **验收与核对（Inspect & Verify）**：检查 Worker 返回的结构化结果信封（`OMP_WORKER_RESULT`），核对文件修改产物与测试验证证据后再决定是否进入下一步。
6. **同会话纠错（In-Session Correction）**：若验收不达标或遇到阻碍，调用 `omp_continue` 注入针对性反馈（feedback）在同一会话中推进纠错，无需从头重跑。

## 3. 执行策略对比矩阵

| 执行模式 | 适用场景 | 核心入口工具 | 安全与使用边界 |
| :--- | :--- | :--- | :--- |
| **直接处理**<br>*(Host-native)* | 单文件微调、即时问答、架构轻量讨论、需人类即时逐行决策的操作。 | 主控内置的 read/edit/终端工具 | 不启动后台 Worker，无额外进程与编排开销。 |
| **单任务委托** | 独立的特性开发、定向 Bug 修复、单子系统重构、耗时技术只读调研。 | `omp_run_compact`<br>*(或 `omp_delegate` + `omp_wait`)* | 需具备清晰的 `goal` 与 `acceptance`。写入任务必须显式声明具体的 `ownership` 路径。 |
| **批量 DAG 编排** | 跨模块系统重构、前后端并行开发、多源并行调研再汇总整合。 | `omp_run_batch_compact`<br>*(配合 `omp_wait_group`)* | 并行 `write` 任务之间必须拥有互斥的 `ownership` 路径。修改相同文件必须声明串行的 `depends_on` 依赖。受 `max_parallel` (1–10) 并发池约束。 |

## 4. 跨 Harness 自然语言委派示例

### 示例 1：只读技术调研
- **用户需求 / 提示词**：“调研一下本仓库的状态持久化与清理机制，列出涉及的文件，不要修改任何代码。”
- **主控动作**：以 `access: "read_only"` 调用 `omp_run_compact`，设定以“识别相关文件并确认未修改任何工作区代码”为验收标准。

### 示例 2：单任务实现与同会话监督纠错
- **用户需求 / 提示词**：“为进程运行器添加指数退避重试，并确保单元测试通过。”
- **主控动作**：首先调用 `omp_run_compact` 分发任务；若验收时发现测试套件遗漏了边界断言，主控直接调用 `omp_continue(job_id, feedback)` 要求在同一会话中补齐测试断言。

### 示例 3：多任务 DAG 批量编排
- **用户需求 / 提示词**：“并行重构认证中间件与用户服务，等两项都完成后再运行完整的集成测试套件。”
- **主控动作**：提交 `omp_run_batch_compact`，子任务 `refactor-auth` 与 `refactor-user-svc` 分别声明互斥的 `ownership` 写入路径，下游的 `run-integration-tests` 则声明 `depends_on: ["refactor-auth", "refactor-user-svc"]`。

## 6. 安全防线与编写个人工作流准则

在公开文档中记录或分享 Agent 工作流时，应清晰区分可复现事实、个人偏好与私有环境：

- **事实与个人偏好分离**：清晰区分协议级技术事实（stdio MCP 通信、DAG 依赖校验、路径隔离）与个人环境选择（特定模型、个人硬件、偏好客户端）。
- **高影响操作由主控与人类确认**：不可逆或高影响动作——如发布包（`npm publish`）、推送分支（`git push`）、生产部署、删除重要数据或修改生产机密——**必须保留在主控 Harness 与人类用户的直接交互中由人类确认**，绝不盲目委派给后台 Worker。
- **保护私人环境信息**：严禁公开本机绝对路径（如本地用户目录或私有磁盘路径；统一使用 `<workspace_path>` 等占位符）、私有 API Token、密钥凭据或账户账单/配额细节。
